# Orbit 功能、AI 接入与验证决策（2026-09）

这份文档区分三件事：

1. 已经可在 iPhone 上侧载验证的功能；
2. App Store 正式版必须用开发者账号、签名或后端才能完整启用的功能；
3. 当前不应实现的功能，避免产品变成另一个泛待办或高风险自动化工具。

## 1. 本轮已接入的产品能力

| 能力 | 当前实现 | 用户看到的行为 | 边界 |
|---|---|---|---|
| 冲突识别与建议重排 | 写入前读取系统日历，找出重叠事件，并找未来 14 天内第一个同等时长空档 | 卡片会显示冲突、冲突事件和“采用建议”按钮 | 绝不自动移动已有日程；目前主要检查本次发生时间，循环日程的每一次未来冲突属于后续增强 |
| 循环日程 | EventKit 循环规则写入系统日历 | 可设每天、工作日、每周、每月、每年、间隔和结束日 | 日历仍是苹果/用户账户自己的日历，Orbit 不自建日历数据库 |
| 循环习惯 | 新增“习惯”入口，建立循环提醒事项 | 习惯出现在苹果“提醒事项”App，可勾选完成 | 习惯不是 Orbit 内部待办；需要提醒事项“完全访问”权限 |
| 日程同步提醒事项 | 选定日程可额外同步成系统提醒事项 | 卡片上可同步或移除同步 | 它与日历提醒是两个独立系统，用户可只用其中一个 |
| 晨间简报 | 前台打开 App 时读当天系统日程，配一句固定的本地鼓励语 | 可在设置中开启/关闭；最多显示前三项 | “起床后”在 iOS 中无法可靠自动判断，因此定义为早晨打开 App 时展示 |
| 本地天气与每天通知 | 用户主动开启本地天气后才请求定位；可设每日本地通知 | 通知提示打开 Orbit，打开后读取最新日程和天气 | WeatherKit 需要正式开发者团队启用权限；侧载期天气可能显示“暂时无法获取”，日程简报仍可用 |
| 系统快捷指令 | App Intents 提供“快速记录日程”“查看今日日程” | 可在快捷指令、Siri、Spotlight 中使用 | 快捷指令只打开/导航到 Orbit，不会绕过用户确认而后台创建日程 |
| 主屏幕小组件 | OrbitWidget 是一个真实的 Widget Extension | “快速记录”小组件一键打开输入框 | 当前是无数据共享的快速入口；显示今日日程需正式 App Group 签名，见第 6 节 |
| API Key 安全迁移 | 旧的 UserDefaults 明文 Key 会迁至 iPhone Keychain | 用户原有 Key 尽量保持可用 | 这是 BYOK 模式的安全底线，不等于已实现会员后台 |

系统日历、提醒事项、通知和天气功能都要在真机逐项授权测试。EventKit 的完全访问权限、提醒事项权限和重复规则由 Apple 的 EventKit 框架管理；本 App 不会绕过系统权限。

## 2. 不应混在一起的四个概念

### 日程

有具体开始/结束时间、地点和日历归属，例如“周三 15:00 组会”。它是系统日历事件，写入苹果日历。

### 循环日程

同一日程按规则重复，例如“每周三组会”。它仍是日历事件，只是有循环规则。

### 习惯

可完成、可重复的行动，例如“每天 22:30 阅读”。它是系统提醒事项，写入苹果提醒事项。

### 提醒

提醒是“何时提醒用户”的机制：

- 日历提醒：绑定日程；
- 提醒事项：可勾选完成；
- Orbit 晨间通知：提醒用户打开 App 看简报。

它们可以关联，但不应合并成一种模糊的数据类型。

## 3. 电话提醒、主动触发与预约协调

### 电话提醒：不建议放进 v1

Orbit 可以提供“拨打电话”按钮，打开 tel: 链接；iOS 会要求用户确认，App 不能静默自动外呼。真正的自动电话提醒需要额外的云通信服务、号码资源、明确同意、退订机制、频率控制、隐私与反骚扰/通信合规处理。这不是一个前端日历功能。

v1 的正确优先级是：日历提醒、提醒事项、本地通知。若以后验证确有高价值，再做“用户点确认后由后端呼叫”的企业/高端服务，而不是自动拨号。

### “主动触发预约协调”是什么意思

它指的是 条件 → 建议/动作，例如：

- 检测到预约与工作日历冲突 → 建议三个可用时间；
- 用户确认后 → 发送一封预约邮件/信息给参与者；
- 对方选择一个时间 → 写回日历。

这会涉及联系人、参与者、邮件/消息、第三方日历 OAuth、后端任务队列和失败补偿。v1 只做到“识别冲突并给出建议”；任何改时间、发消息或预约都必须让用户最后确认。

### 协作与共享建议

先不自建协作账号体系。第一步只使用用户已有的共享 iCloud/Google/Exchange 日历：Orbit 已可向有写入权限的系统日历写事件，成员继续在原生日历中共享、邀请和撤销权限。

只有当目标用户明确需要“排班主管分派、成员确认、多人共同编辑、审计记录”时，再做 Orbit 账号、服务端权限、邀请和团队数据模型。那是一个独立产品阶段。

## 4. BYOK、后台托管 Key 与“Voice Code”

这里应当是 **BYOK**，不是 Voice Code。

**BYOK = Bring Your Own Key**，即“用户自带模型 API Key”。“高级用户”指能理解模型提供商、账单和 Key 风险的技术型用户；它不天然等于付费 Pro 用户。

### 方案 A：BYOK（当前适合封闭测试）

~~~text
用户的 iPhone ──使用用户自己的 Key──> 模型服务商
~~~

- Orbit 不代付模型费用；
- Key 仅保存在此 iPhone 的 Keychain；
- 用户自己申请 Key、承担用量账单；
- 适合邀请少量测试者、快速验证识别质量和产品流程；
- 不适合普通 App Store 消费者：设置门槛高、体验不统一。

当前 App 已采用这个模式，并已把 Keychain 作为保存位置。

### 方案 B：Orbit 托管 Key + 免费额度/会员（面向公开 App Store）

~~~text
iPhone App ──登录/设备令牌、请求内容──> Orbit 后端
Orbit 后端 ──只在服务器保存的供应商 Key──> 模型服务商
~~~

后端必须负责：

1. 身份/设备识别；
2. 每位用户的免费额度、会员权益和速率限制；
3. 输入大小、图片大小、模型白名单；
4. 调用日志、成本账本、异常熔断；
5. StoreKit 内购状态的服务端校验；
6. 供应商 Key 的密钥管理和轮换。

**绝不能**把你的个人供应商 Key 写进 iOS App，或让 App 直接带着你的 Key 请求模型。IPA 可被提取，Key 会泄露；任何人都能消耗你的额度，也无法按用户控制成本。

### 推荐的落地顺序

1. 现在：封闭侧载/TestFlight 用 BYOK，验证产品体验；
2. 识别准确率和留存过关后：做一个很小的 Orbit 后端，给每人受控免费额度；
3. 再做 App Store 内购的订阅/额度包；
4. BYOK 如需保留，只作为“开发者/高级设置”，不能成为绕过公开版数字功能付费的路径。

面向 App Store 用户销售 AI 使用额度、订阅或解锁功能时，应走 Apple 的 In-App Purchase；上线前需逐条核对最新版 App Review Guidelines。

## 5. 免费/付费不是“有没有 AI”，而是管理有限的 AI 成本

Apple 日历已经有日历、提醒和 Siri。Orbit 不能只把“自然语言写日程”叫作差异化，因为 Toki、Smore 等也在做多模态录入。

建议把产品承诺收窄为：

> **把复杂、重复、容易出错的时间表来源，批量变成可核对、可路由、可冲突处理并保留系统日历控制权的日程。**

最值得验证的垂直切口是：课程表、轮转/排班、会议通知和复杂重复日程。它的核心不是“能聊天”，而是：

~~~text
来源（文字 / 语音 / 图片）
    ↓
逐项结构化预览
    ↓
目标日历路由 + 循环规则 + 冲突提示
    ↓
用户确认 / 可回滚
    ↓
苹果系统日历、提醒事项、共享日历
~~~

这不是声称 Orbit 已经比所有竞品强；它是建议的、可测试的差异化方向。若不选择明确人群和高错误成本场景，Orbit 会与泛 AI 日历高度同质。

### 权益的初始假设（不是最终定价）

| 层级 | 建议内容 | 不该作为卖点的内容 |
|---|---|---|
| 免费 | 少量受控 AI 额度、所有已写入日程的编辑/删除、系统日历/提醒事项连接、冲突提示 | 把用户已有的系统日历基本控制权锁住 |
| Plus | 更多文字/语音识别、批量导入、更多冲突建议和循环/路由模板 | “更聪明”但不可解释的自动修改 |
| Pro | 更高的图片/复杂表格额度、排班/学期模板、数据导出/恢复、优先模型 | 让 BYOK 变成规避内购的替代通道 |

最终次数、价格和试用天数不能照抄竞品。必须按真实成本与转化数据决定。

## 6. 如何安全验证模型成本、留存和试用转化

### 不要把 Key 发给 Codex 或贴进聊天

不要在这里、Git 提交、截图、Issue 或 GitHub Actions 日志中粘贴 Key。即使是小额度测试 Key，也应把它放进你自己控制的后端密钥环境中。

如果你愿意给测试预算，正确做法是：

1. 在模型提供商中创建**独立测试项目/独立 Key**，只开放指定模型，设很小预算；
2. 建一个 Orbit 测试后端，Key 只存在其环境变量/密钥管理服务中；
3. 后端额外设置自己的硬性请求/金额上限，不能只依赖提供商的预算提醒；
4. 给 10–30 名测试者发受控免费额度，而不是把 Key 发到客户端；
5. 每天查看成本和错误率，超限自动停止模型调用。

我们可以在后续实现这个后端、预算表和测试埋点；但不应由你把密钥直接交给我保管或贴入代码。

### 每次请求要记录什么

不记录原始私人日程文本/图片作为默认行为。记录最小化、经同意的产品指标：

- 请求类型：文本、语音转写后文本、图片；
- 使用的模型、输入大小、输出大小、延迟、失败原因；
- 是否识别成功、用户是否编辑、是否最终写入日历；
- 首次成功时间、D1/D7 回访、试用开始、付费墙看到、购买成功/退款。

成本公式：

~~~text
单位成功写入成本
=（模型输入成本 + 模型输出成本 + 图片/语音成本 + 后端成本）
  ÷ 成功写入系统日历的次数
~~~

订阅毛利还要扣除 App Store 分成、退款、云服务和支持成本。先测 2–3 个候选模型和真实样本，不要依据单次体验或竞品价格直接定价。

## 7. Widget、WeatherKit 和正式签名

目前小组件是“快速进入 Orbit”的 Widget Extension，因此不需要把聊天或日程数据复制到小组件。要做“今日三项日程”Widget，则需要：

1. 正式 Bundle ID 和付费开发者团队；
2. App Group entitlement；
3. App 与 Widget 之间最小化、可删的数据摘要；
4. Widget 时间线刷新策略和隐私遮罩。

天气同理：WeatherKit 要在 Apple Developer 后台为正式 App ID 启用相应能力。现在不要为了侧载而伪造 entitlement；代码会优雅降级。

## 8. 下一步的验证顺序

1. 推送本轮代码，运行 GitHub Actions 的 Simulator 与 IPA 构建；
2. 用真机授权日历、提醒事项、通知，逐项测循环、删除、冲突、习惯与 Widget；
3. 建立 10 条固定验收案例（含工作日循环、跨日、全天、冲突、无权限、网络失败）；
4. 先招 5–10 位 BYOK 测试者，验证识别准确率和“写入后是否还要手改”；
5. 确定一个垂直场景（优先复杂排班/课程表/轮转）；
6. 决定是否投入后端托管额度与 StoreKit 内购；
7. 之后再进入 App Store 的签名、隐私、截图、TestFlight 和审核流程。
